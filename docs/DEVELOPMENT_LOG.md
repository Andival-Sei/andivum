# Журнал разработки

Этот файл хранит не общий поток отладочных логов, а короткие записи о проблемах,
которые могут повториться. Цель журнала — не искать обход заново, а помнить
причину, постоянное исправление и проверку, которая защищает от регрессии.

## 2026-08-02 — Android Keystore не принял вручную заданный IV

- Симптом: сохранение авторизационного состояния падало с ошибкой Android
  Keystore `Caller-provided IV not permitted`.
- Причина: для AES-GCM ключ Android Keystore должен сам сгенерировать вектор
  инициализации (IV); приложение пыталось передать его при шифровании.
- Постоянное исправление: шифрование начинается без пользовательского IV, после
  чего сохраняется IV, созданный `Cipher`.
- Защита от повторения: `SecureAuthStateStoreTest` проверяет запись и чтение
  состояния на физическом Pixel.
- Статус: исправлено.

## 2026-08-02 — Сертификат сервера нельзя было установить как CA

- Симптом: Android сообщал, что для выбранного файла нужен закрытый ключ.
- Причина: в хранилище центра сертификации выбирался сертификат сервера PFX,
  а не публичный сертификат корневого центра сертификации.
- Постоянное исправление: на телефон установлен только публичный `.crt` корневого
  CA; закрытый ключ и PFX остаются только на машине разработки.
- Защита от повторения: debug Network Security Config доверяет пользовательскому
  CA, но приложение не использует trust-all; release-сборка эту настройку не
  получает.
- Статус: исправлено и проверено на физическом Pixel.

## 2026-08-02 — Физический Android обращался не к тому адресу API

- Симптом: после входа приложение бесконечно ждало ответ, хотя API работал на
  компьютере.
- Причина: `10.0.2.2` — специальный адрес Android Emulator, а подключённый
  телефон не является эмулятором.
- Постоянное исправление: для телефона используется `https://localhost:7240`
  вместе с `adb reverse tcp:7240 tcp:7240`; добавлена команда
  `pnpm android:build:physical`.
- Защита от повторения: перед физическим smoke-тестом проверяются serial
  устройства, `adb reverse` и фактический `BuildConfig.API_BASE_URL`.
- Статус: исправлено.

## 2026-08-02 — API-тесты столкнулись с занятым исполняемым файлом

- Симптом: `pnpm check` не мог заменить `Andivum.Api.exe` во время сборки.
- Причина: локальный development API продолжал работать и удерживал файл.
- Постоянное исправление: перед полной проверкой был остановлен именно процесс
  `Andivum.Api.exe`, удерживавший файл; широкое завершение процессов не
  используется.
- Защита от повторения: перед `pnpm check` проверяется, не запущен ли локальный
  API-процесс; команды запуска и тестирования должны разделять dev-процесс и
  сборку.
- Статус: исправлено; если это повторится, сначала остановить конкретный
  процесс и только потом повторить проверку.

## 2026-08-02 — Обновлённый scope не применялся к уже зарегистрированному клиенту

- Симптом: после добавления `offline_access` новый клиентский код мог получать
  отказ от сервера, если native client был создан старой версией.
- Причина: development seeder раньше пропускал существующий client и никогда не
  сверял его permissions с текущим контрактом.
- Постоянное исправление: seeder теперь применяет актуальный descriptor и к
  существующему client; он добавляет новые разрешения и сохраняет точные redirect
  URI из реестра.
- Защита от повторения: интеграционный тест сначала имитирует старый client без
  `offline_access`, затем запускает seeder и проверяет восстановленное право.
- Статус: исправлено.

## 2026-08-02 — API и Android использовали разные локальные сертификаты

- Симптом: браузер открывался, но AppAuth на Android возвращал `Trust anchor
  for certification path not found` ещё до экрана passkey.
- Причина: API запускался со старым самоподписанным сертификатом `localhost`,
  а на телефон был установлен новый корневой CA. Android доверял CA, но не
  мог подтвердить сертификат, который реально показывал API.
- Постоянное исправление: `pnpm dev:api` теперь автоматически находит или
  создаёт пару «локальный CA + сертификат localhost», экспортирует PFX для
  Kestrel и публичный CA для Android, а Windows доверяет этому же корню.
  Trust-all в приложении не включается.
- Защита от повторения: перед physical smoke сверяется fingerprint
  сертификата API с текущей парой CA/server, а команда запуска сама
  подготавливает сертификат, поэтому ручной экспорт старого dev-сертификата
  не нужен.
- Статус: исправлено; после запуска API с новым flow физический Android вошёл
  и показал «Сервер подтвердил ваш аккаунт.».

## 2026-08-02 — Инструментальный APK-тест был собран не вместе с приложением

- Симптом: первый запуск physical instrumentation падал с `NoSuchMethodError`
  для нового поля `AuthShellState`.
- Причина: APK приложения уже был свежим, а `app-debug-androidTest.apk`
  оставался от предыдущей версии.
- Постоянное исправление: Android APK и test APK теперь собираются одной
  командой перед установкой и запуском instrumentation.
- Защита от повторения: не запускать `adb shell am instrument` после сборки
  только `assembleDebug`; для smoke сначала собирать `assembleDebug
  assembleDebugAndroidTest`, затем устанавливать оба APK.
- Статус: исправлено; physical instrumentation прошёл 5 тестов.

## 2026-08-02 — Интеграционные auth-тесты столкнулись с повторным email

- Симптом: повторный запуск API-теста регистрации получал `Username ... is
  already taken`, хотя сам flow был исправен.
- Причина: выделенная тестовая PostgreSQL-база сохраняет данные между
  отдельными запусками, а тест использовал один фиксированный email.
- Постоянное исправление: синтетические email для registration/sign-in тестов
  получают уникальный GUID на каждый запуск.
- Защита от повторения: тесты сначала создают или регистрируют уникальную
  запись, затем проверяют именно её; реальные пользовательские email в тесты
  не попадают.
- Статус: исправлено.

## 2026-08-02 — Supabase CLI не поднял локальный стек с первого раза

- Симптом: `supabase start` сначала превысил тайм-аут, а облегчённый запуск
  завершился `LegacyStartDbSetupError`/exit 125 с сообщением об отсутствующем
  локальном Supabase profile; контейнеры Supabase не остались запущенными.
- Причина: первый запуск скачивал крупный образ Supabase Postgres и упёрся в
  локальную инициализацию Docker/CLI, а не в ошибку SQL-миграции.
- Постоянное исправление: пока не найдено; запускать Supabase CLI повторно после
  проверки Docker/CLI profile и не считать неудачный старт доказательством
  корректности схемы.
- Защита от повторения: RLS-миграция отдельно проверена в явно названной
  временной базе `andivum_rls_test` на выделенном PostgreSQL-тест контейнере с
  эмулированными `auth.jwt()` claims; база удалена после проверки. Полный
  Supabase local smoke остаётся обязательным после исправления CLI/Docker.
- Статус: SQL migration и RLS проверены; local Supabase stack deferred.

## 2026-08-02 — Auth0/Supabase подготовлены без преждевременного включения cloud flow

- Симптом: live-вход через Auth0 и проверку одного аккаунта на двух устройствах
  нельзя было честно выполнить без Auth0 tenant, Native Applications и Supabase
  project.
- Причина: внешние настройки и publishable values ещё не созданы; локальный
  OpenIddict нужен для продолжения разработки UI и тестов.
- Постоянное исправление: native clients получили явную конфигурацию
  `local`/`auth0-supabase`; внешняя конфигурация требует все обязательные значения
  и не делает silent fallback. Supabase migration/RLS и direct profile client
  хранятся в репозитории.
- Защита от повторения: configuration tests, mocked Windows/Android HTTP tests,
  SQL RLS check и список внешних smoke-проверок в `docs/AUTHENTICATION.md`.
- Статус: локальный каркас готов; cloud smoke ожидает настройки Auth0/Supabase.

## 2026-08-02 — Auth0 CLI и Auth0 MCP используют разные сессии

- Симптом: `auth0 tenants list` через CLI работал, но Auth0 MCP не появлялся
  среди инструментов Codex.
- Причина: CLI авторизуется отдельно, а MCP использует собственный OAuth device
  flow и токен в системном хранилище; у MCP-сессии истёк срок действия.
- Постоянное исправление: глобальный Codex-конфиг использует официальный `npx`
  запуск с зафиксированной версией MCP и `startup_timeout_sec = 60`; MCP нужно
  переавторизовать командой `npx -y @auth0/auth0-mcp-server init`, затем
  перезапустить Codex.
- Защита от повторения: проверять CLI через `auth0 tenants list`, MCP через
  `npx -y @auth0/auth0-mcp-server session`; не передавать CLI-токен в env MCP.
- Статус: конфигурация исправлена; переавторизация MCP и перезапуск Codex ждут
  ручного действия пользователя.

## 2026-08-02 — Supabase MCP получил одинаковую версию для двух миграций

- Симптом: вторая последовательная `apply_migration` завершилась ошибкой
  `duplicate key value violates unique constraint schema_migrations_pkey`.
- Причина: MCP генерирует номер миграции по текущей секунде; два вызова попали
  в одну секунду.
- Постоянное исправление: удалённую миграцию применять последовательно, после
  каждого вызова проверять `list_migrations`, а следующий вызов разносить по
  времени; не считать ошибочный второй вызов применённым.
- Защита от повторения: фактическое состояние дополнительно проверяется через
  `list_tables`, `list_migrations` и SQL-проверку перед повтором.
- Статус: исправлено; вторая миграция применена с уникальной версией.

## 2026-08-02 — Supabase автоматически открыл SECURITY DEFINER RLS-функцию

- Симптом: security advisor сообщил, что `public.rls_auto_enable()` можно было
  вызвать из Data API ролями `anon` и `authenticated`.
- Причина: включённая настройка автоматического RLS создала служебную
  SECURITY DEFINER-функцию с публичным `EXECUTE`.
- Постоянное исправление: миграция
  `20260802155444_revoke_auto_rls_function_execute.sql` отозвала `EXECUTE` у
  `public`, `anon` и `authenticated`, оставив внутреннему `postgres` нужный
  доступ для триггера.
- Защита от повторения: SQL-проверка `has_function_privilege` и security
  advisor после миграции.
- Статус: исправлено; внешние роли не могут вызвать функцию, advisors чистые.

## 2026-08-02 — Supabase advisor нашёл неоптимальные Auth0 RLS-политики

- Симптом: performance advisor нашёл три предупреждения `auth_rls_initplan` в
  политиках `app_profiles`.
- Причина: `auth.jwt()` мог вычисляться для каждой проверяемой строки.
- Постоянное исправление: миграция
  `20260802155708_update_app_profiles_rls_initplan.sql` пересоздала политики с
  формой `((select auth.jwt()) ->> 'sub')`.
- Защита от повторения: статический migration test и повторный performance
  advisor после применения.
- Статус: исправлено; security и performance advisors не находят предупреждений.

## 2026-08-02 — Supabase config push изменил несвязанные Auth-настройки

- Симптом: первый `supabase config push` вместе с Third-party Auth изменил
  локальные URL, MFA и параметры auth-email на удалённом проекте.
- Причина: CLI отправляет весь блок `[auth]`, а не только одну изменённую
  настройку; локальные dev-значения отличались от уже созданного проекта.
- Постоянное исправление: удалённые значения возвращены к исходному состоянию,
  затем повторный push показал `Remote Auth config is up to date`; Third-party
  Auth остался включённым.
- Защита от повторения: перед `config push` проверять полный diff и не передавать
  локальные dev-значения в cloud без явного решения.
- Статус: исправлено; текущие локальный и удалённый Auth-конфиги синхронны.

## 2026-08-02 — Auth0 перенёс управление enabled clients на отдельный endpoint

- Симптом: обновление `connections/:id` с полем `enabled_clients` вернуло HTTP
  400 `Additional properties not allowed`.
- Причина: Auth0 deprecated управление списком приложений через объект
  connection и использует отдельный endpoint `connections/:id/clients`.
- Постоянное исправление: новые приложения включены через PATCH
  `connections/con_rFsHpOnGhxQ3F8o7/clients` с явным статусом для каждого
  Andivum client ID.
- Защита от повторения: перед изменением читается текущий список клиентов, а в
  запрос попадают только новые Andivum IDs.
- Статус: исправлено; старые Assistant-приложения не добавлены.

## 2026-08-02 — Auth0 CLI может вывести client secret необрезанным

- Симптом: необработанный `auth0 api get clients/:id` вернул поля client secret
  в терминал даже для Native public client.
- Причина: Management API отдаёт полное представление клиента, а CLI сам по
  себе не маскирует поля при raw API-запросе.
- Постоянное исправление: для чтения приложений использовать Auth0 MCP с
  маскированием; raw CLI применять только с фильтрацией полей до вывода. Native
  приложения используют `token_endpoint_auth_method=none`, client secret в
  Andivum не используется и не сохранён в проект.
- Защита от повторения: не выполнять необрезанный raw GET клиентов и не
  сохранять его вывод в артефакты/логи.
- Статус: исправлено процедурой; секреты в репозиторий не попали.

## 2026-08-02 — прямой запуск Windows AppX не создавал регистрацию WinUI

- Симптом: запуск готового `Andivum.Windows.exe` завершался с
  `REGDB_E_CLASSNOTREG` в `Microsoft.WindowsAppRuntime.DeploymentManager`.
- Причина: готовый exe запускался напрямую, без package-aware регистрации
  Windows App SDK для debug-пакета.
- Постоянное исправление: добавлена команда `pnpm windows:run`, которая
  запускает проект через `dotnet run`; именно этот путь регистрирует debug
  identity и запускает приложение с нужным контекстом.
- Защита от повторения: `tools/scripts/windows-run.test.mjs` проверяет команду,
  project path, x64 и загрузку `.env.andivum.local`; runtime smoke через
  `dotnet run` подтвердил живое окно Andivum.
- Статус: исправлено; прямой запуск exe не используется как команда разработки.

## 2026-08-02 — PowerShell разделил cloud-параметры Android Gradle

- Симптом: первый cloud-build Android интерпретировал части домена Auth0 и URI
  callback как отдельные задачи Gradle.
- Причина: значения `-P...` с точками и `://` передавались без кавычек через
  `pnpm`/PowerShell.
- Постоянное исправление: добавлена команда `pnpm android:build:cloud`, которая
  читает публичные значения из `.env.andivum.local` и передаёт их Gradle как
  отдельные аргументы. Ручной пример в `docs/AUTHENTICATION.md` также заключает
  каждый `-P...` аргумент в кавычки.
- Защита от повторения: рабочая команда с теми же параметрами собрала
  `assembleDebug` и `assembleDebugAndroidTest`; для конфигурации Andivum
  используй копируемый пример, не набирай параметры вручную.
- Статус: исправлено; Android cloud-build проходит при использовании
  документированной команды.

## Правило для новых записей

Новая запись появляется после проблемы с практическим влиянием на разработку,
а не после каждого обычного предупреждения. Для каждой записи обязательны
симптом, причина, постоянное исправление, регрессионная защита и статус.
