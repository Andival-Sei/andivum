# Native authentication shell UI

- Дата: 2026-08-02
- Статус: accepted
- Владелец: AI под продуктовым руководством владельца Andivum

## Намерение

Превратить техническую auth-заглушку в первый настоящий пользовательский
срез. При запуске пользователь должен сразу понимать, что такое Andivum и
зачем нужен passkey. После успешного входа он должен увидеть пустое личное
пространство, а не технический текст о завершившемся OAuth-потоке.

## Наблюдаемое поведение

1. Given нет сохранённой сессии, When приложение запускается, Then показывается
   экран входа с названием Andivum, коротким объяснением и одной основной
   кнопкой входа через passkey.
2. Given вход выполняется, When пользователь нажал основную кнопку, Then она
   становится недоступной, а рядом отображается понятное состояние ожидания.
3. Given passkey-flow успешно завершился, When приложение получает callback и
   токены, Then показывается авторизованное личное пространство с placeholder-
   карточками Tasks и Finance.
4. Given сохранённая сессия уже существует, When приложение запускается, Then
   сразу показывается личное пространство без повторного входа.
5. Given пользователь нажал «Выйти», When локальная сессия очищена, Then
   приложение возвращается на экран входа.
6. Given системная локаль поддерживается, When приложение отображает этот UI,
   Then используются `en-US` или `ru-RU`; неизвестная локаль получает русский
   fallback согласно существующей policy.
7. Given системная тема светлая или тёмная, When приложение запускается, Then
   UI следует системной теме без отдельного переключателя на этом шаге.

## Границы

### Входит

- Нативный экран входа Android Compose и Windows WinUI 3.
- Нативный авторизованный shell с пустыми карточками Tasks и Finance.
- Состояния initial, loading, signed-in, error и signed-out.
- Локализованные пользовательские строки для `en-US` и `ru-RU`.
- Светлая/тёмная системная тема.
- Сохранение текущего OIDC + PKCE и secure token storage.

### Не входит

- Реальные данные задач и финансов.
- Навигация в полноценные модули.
- Account profile, avatar, recovery и logout-all-devices.
- Ручной выбор языка или темы.
- Общий UI-runtime между Kotlin и C#.

## Ошибки и восстановление

- Ошибка discovery, callback или token exchange остаётся на экране входа и
  отображается человеческим сообщением.
- Повторное нажатие основной кнопки во время запроса блокируется.
- Выход очищает локальные токены; серверная глобальная ревокация остаётся
  отдельной auth-задачей.

## Данные и безопасность

- UI не показывает и не логирует access/refresh tokens, authorization code или
  passkey payload.
- Вход продолжает выполняться через системный браузер.
- Android хранит AuthState в Android Keystore-backed storage, Windows — в
  Windows Credential Locker.

## Платформенные различия

- Windows: desktop-композиция с боковой навигационной рамкой и крупным
  welcome-блоком; Mica и системные WinUI-контролы.
- Android: вертикальный Compose layout, карточки и компактный нижний
  навигационный placeholder, адаптированный под узкий экран.

## Критерии приёмки

- [ ] На обеих платформах есть отдельный экран входа и отдельный signed-in
      placeholder.
- [ ] Повторный запуск после успешного входа не показывает ложный экран
      «не авторизован».
- [ ] Logout возвращает пользователя на экран входа.
- [ ] Строки UI не захардкожены в Kotlin/C# presentation-коде.
- [ ] Android поддерживает системную светлую и тёмную тему.
- [ ] Реальный passkey-flow не регрессирует.
- [ ] Скриншоты Android и Windows проверены; статическая сборка не считается
      UI-проверкой.

## Проверки

- [ ] Unit/instrumentation: state transitions.
- [ ] Integration: существующие API/auth tests.
- [ ] Windows UI: запуск packaged/unpackaged shell и визуальная проверка.
- [ ] Android UI: установка на физический Pixel и визуальная проверка.
- [ ] Security: tokens remain in OS-protected storage.
- [ ] Localization/theme/accessibility: обе локали, системная тема, touch
