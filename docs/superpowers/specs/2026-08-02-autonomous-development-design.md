# Автономный AI-driven процесс разработки

- Дата: 2026-08-02
- Статус: утверждено владельцем
- Область: весь репозиторий Andivum

## Намерение

Владелец продукта не пишет код. Он описывает желаемый результат, ограничения и
свои впечатления от продукта. AI-агент самостоятельно переводит это в
спецификацию, архитектуру, тесты, реализацию, проверку и опубликованные
изменения.

Процесс должен сохранять скорость индивидуального pet-проекта, но не обменивать
её на хрупкость в аутентификации, финансах, синхронизации и интеграциях.

## Рассмотренные подходы

### Полный ручной контроль владельца

Каждая спецификация, план, зависимость и commit ожидают подтверждения. Этот
режим прозрачен, но превращает владельца в диспетчера инженерного процесса и
противоречит цели «я говорю, чего хочу».

### Быстрый prompt-to-code

Агент сразу реализует запрос, а тесты и документация добавляются после. Режим
даёт быстрые демо, но особенно опасен для финансов, auth и многомодульных
взаимодействий.

### Автономный spec-first TDD

Агент сам выполняет короткий design/spec/plan цикл, затем работает через
Red-Green-Refactor, независимую проверку и CI. Владелец не подтверждает рутинные
шаги. Это выбранный подход.

## Роли

### Владелец

- задаёт проблему, желаемое ощущение и приоритет;
- сообщает о фактическом поведении приложения;
- может в любой момент изменить направление;
- предоставляет секреты или выполняет действия, которые нельзя делегировать.

### AI-агент

- исследует текущий код и документацию;
- устраняет безопасную неоднозначность разумными допущениями;
- создаёт и поддерживает спецификации, ADR и планы;
- реализует production-поведение через TDD;
- запускает проверки на реальных доступных платформах;
- делает code/security review;
- ведёт Git и GitHub до проверенного результата;
- честно разделяет автоматические, статические и живые UI-проверки.

## Автономность

Агент не останавливается для обычных:

- технических решений внутри принятой архитектуры;
- добавлений проверенных бесплатных зависимостей;
- локальных обратимых изменений toolchain;
- создания веток, worktrees, commits, pull requests и merge при зелёном CI;
- исправления найденных тестами, review или CI дефектов;
- синхронизации документации.

Обязательная пауза остаётся только при отсутствии необходимой власти или
информации: платёж, принятие юридических условий, передача недоступного секрета,
удаление существенных внешних данных, изменение публичной security boundary или
другое труднообратимое действие вне уже заданной цели.

## Рабочий цикл

1. **Intent.** Запрос владельца переводится в наблюдаемое пользовательское
   поведение.
2. **Context.** Читаются `AGENTS.md`, `PROJECT_CONTEXT.md`, архитектура и
   затрагиваемый код.
3. **Design.** Для существенной функции сравниваются варианты и выбирается
   минимальный, не закрывающий будущее развитие.
4. **Spec.** Фиксируются сценарии, границы, ошибки и критерии приёмки.
5. **Plan.** Работа дробится на короткие проверяемые задачи.
6. **TDD.** Каждое production-поведение проходит Red-Green-Refactor.
7. **Review.** Проверяются соответствие spec, качество, безопасность и лишний
   scope.
8. **Platform QA.** Выполняются доступные Windows/Android/API проверки;
   непроверенное явно называется непроверенным.
9. **Delivery.** Commit, push, CI, PR/merge и проверка синхронизации Git.
10. **Record.** Обновляются roadmap, ADR и пользовательская документация.

## TDD-контракт

Для feature, bugfix, refactoring и изменения поведения production-код не пишется
до теста, который был запущен и упал по ожидаемой причине.

Владелец заранее разрешает исключения только для:

- generated code;
- декларативной конфигурации и документации;
- одноразового технического spike, который удаляется до production-реализации.

Если spike сохраняется в продукте, его реализация переписывается через TDD.

## Уровни проверки

- domain unit tests;
- module integration tests с реальной PostgreSQL через container;
- OpenAPI contract/generation checks;
- WinUI unit и UI-thread tests;
- Android JVM, Compose UI и managed-device tests;
- Appium end-to-end для ключевых Windows-сценариев;
- security review для Identity, Finance, Integrations и sync;
- ручной live UX review владельцем после доступной сборки.

## Creator Vibe

Для пользовательских функций агент сохраняет не только буквальное требование, но
и намерение: приложение должно ощущаться быстрым, спокойным, честным и
принадлежащим пользователю. Магия может убирать рутину, но не скрывать данные,
решения и последствия.

## Definition of Done

Функция завершена, когда:

- выполнены критерии spec;
- тесты доказали Red и проходят Green;
- полный релевантный набор проверок зелёный;
- нет открытых критичных review/security findings;
- локализация, тема, accessibility и ошибки учтены там, где применимо;
- документация синхронизирована;
- изменение опубликовано, CI зелёный, локальный HEAD синхронизирован с remote;
- итог сообщает фактически выполненные проверки и оставшиеся ограничения.

## Границы текущего внедрения

На этом этапе создаются постоянные инструкции, шаблоны и `doctor`. Полный
application CI, Appium и Gradle Managed Devices подключаются вместе с
соответствующими project skeletons, чтобы не хранить неисполняемую конфигурацию.
