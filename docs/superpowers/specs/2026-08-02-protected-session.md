# Protected session vertical slice

- Статус: реализовано; Windows Hello и полноценный cross-device smoke требуют
  ручного шага
- Дата: 2026-08-02

## Цель простыми словами

После входа приложение должно спросить сервер: «Этот пользователь действительно
вошёл?». Сервер отвечает только клиенту с действительным access token (коротким
пропуском). Если короткий пропуск истёк, клиент один раз получает новый через
refresh token из защищённого хранилища и повторяет запрос. Пользователь не
должен замечать обновление.

Обе платформы используют один и тот же endpoint и получают один стабильный
идентификатор пользователя. Это даёт проверяемое доказательство, что Windows и
Android работают с одной серверной учётной записью, а не с двумя локальными
сессиями.

## Границы

Входит:

- разрешить native-клиентам запрашивать `offline_access`, необходимый для
  refresh token;
- проверить защищённый `GET /api/v1/session`;
- автоматически обновлять access/refresh token при истечении или ответе `401`;
- сохранять новые токены только в Windows Credential Locker или Android
  Keystore-backed storage;
- показывать в обоих dashboard результат проверки сервера без показа токена;
- покрыть анонимный доступ, успешный ответ, refresh и ошибку восстановления
  тестами.

Не входит:

- logout-all-devices;
- account recovery;
- семейные пространства;
- реальный Windows Hello smoke без ручного подтверждения пользователя.

## Критерии готовности

- Сохранённый, но просроченный access token не открывает dashboard без проверки
  сервера.
- При наличии действительного refresh token клиент получает новую пару токенов,
  сохраняет её и повторяет защищённый запрос максимум один раз.
- Старый refresh token не попадает в URL, UI, логи или тестовый вывод.
- Анонимный запрос к `/api/v1/session` получает `401`.
- Windows и Android используют одинаковый `userId` из ответа сервера для одного
  аккаунта; в UI показывается только понятный статус, не технический секрет.
