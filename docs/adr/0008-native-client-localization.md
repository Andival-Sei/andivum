# ADR 0008: Нативная локализация Windows и Android

- Статус: принято
- Дата: 2026-08-02
- Заменяет: нет

## Контекст

Первый продуктовый срез Andivum должен с самого начала поддерживать русский и
английский языки на Windows 11 и Android. Клиенты будут отдельными нативными
приложениями на WinUI 3 и Jetpack Compose, поэтому локализация должна работать
с системными механизмами каждой платформы и не создавать третий общий runtime.

Нужно также определить поведение при выборе языка системой и при ручном
переключении. Важно различать техническую базовую локаль ресурсов и политику
выбора языка для пользователя:

- `defaultLocale: en-US` остаётся исходной и технической fallback-локалью
  ресурсов;
- `systemLocaleFallback: ru-RU` используется, если язык системы невозможно
  определить или он не поддержан приложением.

## Варианты

### Вариант A: единый JSON runtime-локализации

Плюс — единый формат переводов. Минусы — собственные загрузка, fallback,
pluralization и форматирование, отдельные интеграции с XAML и Compose, а также
дублирование системных возможностей платформ.

### Вариант B: нативная локализация каждой платформы

Windows использует MRT Core и `.resw`, Android — `strings.xml` и `plurals`.
Плюсы — системный выбор языка, корректная интеграция с UI-фреймворками,
платформенные настройки и стандартное форматирование. Минус — переводы и
часть инфраструктуры нужно поддерживать в двух нативных форматах.

## Решение

Выбран вариант B:

1. Windows использует `Strings/en-US/Resources.resw` и
   `Strings/ru-RU/Resources.resw`.
2. Android использует `res/values/strings.xml` как английскую базу и
   `res/values-ru/strings.xml` для русского перевода.
3. По умолчанию клиент пытается определить язык системы: `ru-*` выбирает
   `ru-RU`, `en-*` — `en-US`.
4. Если системный язык нельзя прочитать или он не поддержан, выбирается
   `systemLocaleFallback`, то есть `ru-RU`.
5. Пользователь может выбрать `System`, `English` или `Русский`. Выбор
   хранится локально на конкретном устройстве и не синхронизируется как часть
   аккаунта.
6. Для Android используется AndroidX per-app language API. Для Windows —
   `ApplicationLanguages.PrimaryLanguageOverride`; смена языка может вступать в
   силу после перезапуска окна или приложения.
7. Множественные числа реализуются средствами платформы: Android `plurals`,
   Windows — единым сервисом категорий `one/few/many/other`.
8. Backend возвращает стабильные коды ошибок, а не локализованные UI-сообщения.
9. Переводы не объединяются в общий runtime JSON. Общими остаются product
   configuration, ключи/глоссарий, golden cases и CLI-проверка полноты.

## Последствия

Платформенный UX и системные настройки остаются нативными, а клиенты не получают
лишнюю runtime-зависимость. Цена решения — дублирование переводов и необходимость
проверять совпадение ключей, placeholders и plural-форм между платформами.

Полноценная реализация начинается после создания Windows и Android shell-
проектов. До этого репозиторий фиксирует контракт и проверяет только product
configuration; создавать пустые платформенные каталоги ресурсов в backend
skeleton не требуется.
