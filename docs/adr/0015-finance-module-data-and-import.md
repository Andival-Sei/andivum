# ADR-0015: модель финансовых транзакций и безопасный импорт

- Статус: принято
- Дата: 2026-08-03
- Заменяет: нет

## Контекст

Финансовая операция может состоять из нескольких позиций, каждая позиция имеет
свою вложенную категорию. Источником может быть ручной ввод, фото чека, PDF,
EML или банковский файл. OCR и генеративная модель ошибаются, а повторный
импорт часто создаёт дубли. Клиенты Andivum работают напрямую с Supabase Data
API и должны сохранить изоляцию данных через RLS.

## Варианты

### Вариант A: плоская операция с одной категорией

Просто реализуется, но теряет детали чека и не поддерживает split transaction.

### Вариант B: заголовок + строки + дерево категорий, атомарная RPC-запись

Требует больше схемы, зато сумма и принадлежность строк проверяются одной
серверной операцией; черновик импорта можно отредактировать до записи.

### Вариант C: отправлять исходный файл сразу в backend/LLM

Упрощает клиент, но требует постоянного секретного backend-провайдера, создаёт
дополнительное хранение персональных документов и противоречит текущему
managed-MVP без отдельного API для AI.

## Решение

Выбран вариант B. Финансовый модуль использует:

- целые `bigint` minor units для денег;
- `finance_transactions` и `finance_transaction_items`;
- `finance_categories` с `parent_id`, системными и пользовательскими узлами;
- `finance_create_transaction(payload jsonb)` с проверкой владельца счёта,
  типа категории, суммы строк и idempotency/import fingerprint;
- private Storage для оригинала, если пользователь явно сохраняет вложение;
- локальный OCR/парсер текста как первый этап и Gemini structured JSON как
  опциональный второй этап;
- Gemini key только в PasswordVault/Android Keystore. AI не является
  авторитетным источником суммы, даты или категории.

## Последствия

Плюсы:

- операции с несколькими позициями не требуют обходных записей;
- сервер гарантирует базовые денежные инварианты;
- импортируемый результат всегда виден пользователю до сохранения;
- можно добавлять новые AI/OCR провайдеры без смены модели данных;
- RLS и приватное Storage не дают одной учётной записи читать другую.

Стоимость и ограничения:

- обеим нативным платформам нужно поддерживать одинаковый DTO/JSON контракт;
- локальный OCR зависит от возможностей платформы;
- пользователь самостоятельно отвечает за внешний Gemini API key и его тариф;
- полноценный offline conflict resolution остаётся отдельной задачей roadmap.
