# ADR 0012: Email/password как основной способ входа

- Статус: принято
- Дата: 2026-08-02
- Область: Identity, Windows, Android
- Заменяет: часть решения [ADR 0010](0010-passwordless-account-bootstrap.md)

## Контекст

Пользователю нужен рабочий первый вход на Windows и Android уже сейчас. Полагаться
только на passkey неудобно: на новом устройстве ещё нет подключённого credential,
а восстановление аккаунта пока не спроектировано.

При этом пароль нельзя передавать из нативного приложения напрямую в API или
встраивать в WebView. Нативные приложения уже используют системный браузер и
OIDC Authorization Code + PKCE, поэтому серверная страница авторизации может
безопасно обслужить и регистрацию, и вход.

## Решение

1. Основной путь регистрации и входа — email + пароль на server-rendered auth
   surface `/connect/authorize`.
2. Нативные клиенты открывают системный браузер и не получают пароль. Они
   продолжают использовать Authorization Code + PKCE и тот же token/session flow.
3. ASP.NET Core Identity отвечает за хэширование пароля, нормализацию email,
   валидацию пароля и временную блокировку после неудачных попыток.
4. Passkey остаётся дополнительным способом входа для уже подключённого
   credential и подключается только после обычного входа на странице настроек
   аккаунта. Анонимная регистрация через passkey больше не является основным
   пользовательским сценарием.
5. На локальном MVP email не подтверждается письмом: почтовый провайдер ещё не
   выбран. Email verification, recovery и logout-all-devices остаются отдельными
   задачами перед production.

## Security review

- OAuth Resource Owner Password Credentials и собственный password API не
  добавляются.
- Password POST защищён anti-forgery token и не содержит пароль в URL, логах или
  authorization callback.
- Вход при ошибке использует общее сообщение, чтобы не раскрывать существование
  email; Identity lockout ограничивает перебор паролей.
- Нативные access/refresh tokens остаются только в защищённых хранилищах ОС.
- Email verification и recovery обязательны для production-публикации, даже если
  локальный MVP временно принимает email без письма.

## Последствия

Пользователь может зарегистрироваться на одной платформе и войти на другой с
теми же email и паролем. Passkey не блокирует создание аккаунта и может быть
добавлен позже в настройках. Серверная auth-страница становится частью общего
контракта для Windows, Android и будущего веб-клиента.
