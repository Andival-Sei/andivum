# ADR-0014: Supabase Auth как единственный источник identity

- Статус: Принято
- Дата: 2026-08-02
- Заменяет: ADR-0013, ADR-0012

## Контекст

Первый вариант Andivum использовал Auth0 для email/password через системный
браузер, а Supabase — только для данных. На практике Auth0-сессия не
проходила проверку Supabase Data API: после успешного входа Auth0 приложение
получало `401` при обращении к `app_profiles`. Для владельца проекта также
важно, чтобы обычные email/password вход и регистрация происходили прямо в
нативном интерфейсе Android и Windows.

## Решение

Supabase Auth становится единственным identity provider первого облачного MVP.

- Android и Windows отправляют email/password напрямую в Supabase Auth API по
  HTTPS.
- Регистрация, вход, выход, refresh сессии и восстановление пароля являются
  нативными use cases клиентов.
- Access/refresh tokens хранятся только в защищённых хранилищах ОС.
- `public.app_profiles.user_id` — UUID пользователя из `auth.users`; RLS
  использует `(select auth.uid()) = user_id`.
- Профиль создаётся через защищённый bootstrap-запрос после успешного входа.
- Google, Steam и другие внешние OAuth-провайдеры подключаются позже и могут
  использовать системный браузер.
- Passkeys подключаются отдельным срезом после проверки стабильности текущего
  нативного email/password flow. Их поддержка Supabase на момент решения
  экспериментальная/Beta.
- Auth0 tenant, приложения, Actions и Third-party Auth configuration удаляются
  после проверки миграции; они больше не являются частью runtime или
  конфигурации Andivum.

## Последствия

Положительные:

- обычный вход и регистрация не открывают браузер;
- один Supabase account одинаково работает на Windows и Android;
- Auth, Postgres и RLS используют один идентификатор пользователя;
- исчезает отдельная граница доверия Auth0 → Supabase.

Ограничения:

- подтверждение email и восстановление пароля требуют настроенной почты;
- внешний OAuth и часть passkey-сценариев используют системные OS/browser API;
- SDK не является общим runtime: клиенты остаются нативными, а общий контракт
  задаётся HTTP/JSON и одинаковыми тестовыми сценариями.

## Безопасность

- В клиентских сборках разрешены только Supabase URL и publishable key.
- Service-role/secret key никогда не попадает в Android APK, Windows MSIX,
  тестовые fixtures или логи.
- Клиент не передаёт `user_id` для выбора владельца профиля: его подставляет
  `auth.uid()` из проверенного JWT.
- Email не используется как ключ авторизации.
