# AGENTS.md

## Обязательный контекст

Перед проектированием или изменением кода прочитай в указанном порядке:

1. `PROJECT_CONTEXT.md`;
2. `docs/DEVELOPMENT_PROCESS.md`;
3. `config/product.json`;
4. `docs/ARCHITECTURE.md`;
5. `docs/DECISIONS.md` и относящиеся к задаче ADR;
6. `docs/ROADMAP.md`.

Если задача затрагивает поведение продукта, дополнительно прочитай
`docs/PRODUCT.md`.

## Среда и команды

- Основная среда разработки: Windows 11 и PowerShell.
- Используй `pnpm`, а не `npm`.
- Корневые `pnpm`-команды являются единым интерфейсом репозитория.
- Не считай окружение полноценным Linux/POSIX.
- Используй `rg`, `fd`, `jq` и `deno`, если они упрощают задачу.
- Сообщения коммитов: Conventional Commits на русском языке.

## Понятное общение и учёт проблем

- Всегда отвечай владельцу проекта на русском языке и человеческим языком.
- Сначала сообщай результат простыми словами, затем при необходимости
  объясняй технические детали. Каждый специальный термин сразу расшифровывай.
- Не заставляй владельца разбираться в названиях протоколов, ошибок и команд,
  если можно объяснить смысл обычной фразой.
- Если во время работы обнаружена проблема, не ограничивайся обходом:
  воспроизведи её, найди причину, внеси постоянное исправление, добавь
  регрессионную проверку и запиши результат в `docs/DEVELOPMENT_LOG.md`.
- Временный обход явно помечай как временный и не считай задачу законченной,
  пока постоянное решение не добавлено или причина отложенного решения не
  зафиксирована.
- Перед повтором уже встречавшейся команды или сценария сначала проверь журнал
  разработки, чтобы не повторять известную ошибку.

## Архитектурные ограничения

- Windows-клиент остаётся нативным: C#/.NET/WinUI 3.
- Android-клиент остаётся нативным: Kotlin/Jetpack Compose.
- Не внедряй .NET MAUI, Compose Multiplatform, Electron, Flutter или React
  Native без нового принятого ADR.
- Общие бизнес-инварианты по возможности реализуются на backend.
- Общие API-модели генерируются из `contracts/openapi`; сгенерированный код не
  редактируется вручную.
- Клиенты не обращаются к таблицам или хранилищу другого модуля напрямую.
- Межмодульное взаимодействие идёт через публичные use cases, контракты или
  доменные события.
- Не добавляй третий язык для общего runtime-ядра до появления измеримой
  проблемы, которую нельзя решить контрактами и серверной логикой.

## Идентичность продукта

- Отображаемое имя берётся из `config/product.json`.
- Не размножай литерал `Andivum` по исходникам и манифестам; используй
  генерируемые ресурсы или build properties.
- Не меняй `androidApplicationId`, package identity, backend namespace или
  passkey Relying Party ID как обычный ребрендинг. Для этого нужен отдельный
  план миграции и ADR.

## Безопасность

- Не коммить секреты, access/refresh tokens, signing keys и реальные `.env`.
- Email/password-аутентификация нативных клиентов выполняется напрямую через
  Supabase Auth API по HTTPS, без браузера и embedded WebView.
- Внешний OAuth и passkeys могут использовать системный браузер или системный
  credential UI в отдельных задачах; embedded WebView для входа запрещён.
- Passkeys требуют HTTPS и явно заданного Relying Party ID в production.
- Токены хранятся только в защищённом хранилище ОС.
- Интеграционные OAuth-токены шифруются на сервере и не логируются.

## Качество изменений

- Для feature, bugfix, refactoring и изменения поведения используй строгий
  Red-Green-Refactor: production-код появляется только после теста, который был
  запущен и упал по ожидаемой причине.
- Разрешённые владельцем исключения: generated code, декларативная
  конфигурация/документация и удаляемый технический spike.
- Для Identity, Finance, Integrations и sync обязателен security review.

Перед завершением задачи выполни релевантные проверки, затем минимум:

```powershell
pnpm check
git diff --check
git status --short --branch
```

Не заявляй о проверке Windows или Android UI, если выполнялись только
статические проверки. Не смешивай несвязанные изменения в одном коммите.

## Документация решений

- Значимое архитектурное решение оформляй отдельным ADR в `docs/adr/`.
- Изменение принятого решения не удаляет старый ADR: создай новый и пометь
  прежний как заменённый.
- После изменения границ модулей, стека или протоколов синхронизируй
  `PROJECT_CONTEXT.md`, `docs/ARCHITECTURE.md` и `docs/DECISIONS.md`.

## Интерфейс для AI и автоматизации

- Сначала добавляй детерминированную CLI-команду, затем при необходимости
  оборачивай её MCP-инструментом.
- MCP не встраивается в production-клиенты и не получает прямой доступ к
  production-базе.
- Автоматизация должна поддерживать machine-readable вывод (`--json`) и
  предсказуемые exit codes.

## Автономный режим

- Не запрашивай подтверждение для рутинных design/spec/plan шагов, обратимых
  изменений, бесплатных зависимостей, commits, pull requests и merge при зелёных
  обязательных проверках.
- Задавай вопрос только когда безопасное допущение заметно изменит продукт или
  нужны недоступные полномочия, секреты, платёж, юридическое решение либо
  труднообратимое внешнее действие.
- Для production feature используй ветку `agent/<description>`; крупный план
  можно выполнять в отдельном worktree.
- Веди spec в `docs/superpowers/specs/` и implementation plan в
  `docs/superpowers/plans/`.
